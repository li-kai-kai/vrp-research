# 汶川容量渐进恢复 Pareto 实验：参数与结果分析

## 1. 实验目的与证据边界

本次实验验证三件事：

1. NSGA-II 搜索过程中发现的非支配解是否能跨代保存，而不是只输出单一代表解；
2. 每个非支配解的完整维修顺序、维修队分配和配送优先级是否可审计；
3. 基础容量与容量压力场景下，累计未满足、加权时间成本和最低满足率之间呈现什么近似 Pareto 权衡。

本次结果是 **3 个算法随机种子的原型计算结果**，不是正式论文 benchmark。当前局部强化仍是 `NSGA-II-ALNS-prototype`，尚未实现基于历史绩效更新算子权重的真正 adaptive ALNS；道路容量、PCU、车型阈值仍是场景参数。

## 2. 输出实现

`scripts/reproduce/capacity_recovery.py` 现在维护跨代外部 Pareto archive。archive 按完整决策染色体去除重复个体，再保留所有未被支配的解。

每个结果目录包含：

| 文件 | 内容 |
|---|---|
| `pareto_front_runs.csv` | 每个算法随机种子独立发现的完整非支配 archive |
| `pareto_front.csv` | 合并所有运行后再次非支配筛选得到的全局近似 Pareto 前沿 |
| `pareto_solutions.json` | 每个解的完整维修顺序、维修队分配、配送优先级、目标和辅助指标 |
| `experiment_manifest.json` | 命令、Git SHA/dirty 状态、源文件 SHA-256、Python/平台、算法参数、实例参数、车辆和恢复阶段 |
| `pareto_front.png` | F1、F2 和最低满足率的三联 Pareto 图 |
| `runs.csv` | 每次运行的代表解和运行时间 |
| `convergence.csv` | 每代代表解轨迹 |

其中 `runs.csv` 的代表解采用“最低满足率优先，其次 F1，再其次 F2”的词典序，仅用于兼容原有摘要；完整研究判断应使用 `pareto_front.csv`。

## 4. 目标函数口径

| 目标 | 代码口径 | 优化方向 |
|---|---|---|
| F1 | 9 个周期的 `1-total_satisfaction` 之和，单位为“未满足比例—周期” | 最小化 |
| F2 | 配送车辆通行时间 + `0.05 ×` 规划期内维修作业工时，单位为加权分钟 | 最小化 |
| F3 | `-final_min_satisfaction` | 最小化，即最大化最终最低满足率 |

F1 当前不是吨—周期累计未满足需求。正式论文若使用 `sum_t sum_i r_i^t`，需同步修改代码或同时输出 unmet ton-hours。

## 5. Pareto 结果汇总

### 5.1 基础容量 `capacity_scale=1.0`

| 指标 | 结果 |
|---|---:|
| 每次运行 archive 解数 | 18 / 14 / 17 |
| 合并后的全局非支配解 | 19 |
| 三次运行时间 | 31.21 / 36.87 / 40.39 秒 |
| F1 范围 | 2.466860 – 4.087134 |
| F2 范围 | 75,331.50 – 122,419.83 分钟 |
| 最低满足率范围 | 0 – 0.797307 |
| 最终总满足率范围 | 0.596638 – 0.797307 |
| 平均可达率范围 | 0.736508 – 0.949206 |
| 最终完全修复比例范围 | 0.75 – 1.00 |
| 最大边利用率范围 | 0.0225 – 0.0353 |
| 容量阻塞吨数 | 全部为 0 |

代表性方案：

| 偏好 | seed / solution | F1 | F2 | 最低满足率 | 总满足率 | 维修完成率 | 车辆趟数 |
|---|---|---:|---:|---:|---:|---:|---:|
| 服务优先 | 30003 / `p0011` | 2.466860 | 122,419.83 | 0.797307 | 0.797307 | 0.9375 | 881 |
| 归一化折中 | 30003 / `p0004` | 2.758617 | 88,973.83 | 0.797307 | 0.797307 | 0.9375 | 740 |
| 成本优先 | 30003 / `p0012` | 4.087134 | 75,331.50 | 0 | 0.596638 | 0.8125 | 630 |

从服务优先切换到折中方案，F1 增加约 0.292 个未满足比例—周期，但 F2 减少约 33,446 分钟，最终总满足率和最低满足率保持在理论供给上限。与成本优先相比，折中方案增加约 13,642 分钟，却把最终总满足率从 59.66% 提高到 79.73%，并消除最差需求点零满足的结果。

基础容量下最大边利用率仅 3.53%，容量约束没有形成实质瓶颈；该场景主要体现维修可达性、配送时间和公平性之间的权衡，不能用来证明容量机制的政策作用。

代表性方案：

| 偏好 | seed / solution | F1 | F2 | 最低满足率 | 总满足率 | 维修完成率 | 最大边利用率 |
|---|---|---:|---:|---:|---:|---:|---:|
| 服务优先 | 30002 / `p0021` | 2.463882 | 143,991.50 | 0.797307 | 0.797307 | 1.0000 | 0.8333 |
| 归一化折中 | 30002 / `p0003` | 2.644867 | 92,648.50 | 0.797307 | 0.797307 | 1.0000 | 0.5700 |

容量缩放到 5% 后，Pareto 解的最大边利用率达到 45.5%–97.7%，说明容量约束已接近或达到活跃区间。尽管如此，当前全局 Pareto 解的 `capacity_blocked_tons` 仍为 0，表示调度器能通过车辆选择、路径重算和减少运输量找到容量可行方案；因此该档位可以称为“容量紧张”，但不能称为“产生未消化容量阻塞”。若要研究显式阻塞效应，应进一步检查 `capacity_scale=0.02`。

服务优先方案比折中方案额外减少约 0.181 个未满足比例—周期，但增加约 51,343 分钟的 F2；折中方案已达到供给约束下的最高总满足率和最低满足率，因此更接近当前目标尺度下的管理折中点。

## 6. 跨场景解释

1. 两个场景都出现最低满足率为 `0` 或 `0.797307` 的明显分层。原因是当前 max-min 配送逻辑：只要所有需求点最终可达，就倾向于把各点同时提升到供给约束上限；若至少一个需求点始终不可达，最低满足率直接变为 0。F3 因而缺少中间梯度，后续应增加 deprivation、加权 unmet demand 或 Gini/Atkinson 等连续公平指标。
2. 基础场景容量利用率极低，容量创新在默认参数下基本不影响可行性；5% 压力场景才真正检验容量机制。
3. 压力场景的最优 F1 略低于基础场景，不应解释为“容量越小绩效越好”。在相同决策下，更宽松容量不可能更差；该反常排序来自有限种群、有限代数和随机启发式产生的近似前沿误差，说明正式比较必须提高计算预算并报告多种子 HV/IGD+。
4. 当前三次运行的 archive 大小和代表解仍有明显差异，前沿尚不能视为收敛。正式论文至少需要 20–30 个算法随机种子、固定函数评价预算、全局参考集、HV/IGD+ 和置信区间。
5. 本次所有方案均达到供给约束上限或明显低于上限；`time-to-80% total demand` 在当前供需下不可达，管理 KPI 应使用 75% 或“达到理论上限的 80%”。

## 7. 复现命令

基础容量：

```bash
uv run python scripts/reproduce/capacity_recovery.py \
  --scenario wenchuan --seeds 3 --seed-start 1 \
  --pop-size 24 --generations 20 \
  --crossover-probability 0.9 --mutation-probability 0.2 \
  --alns-iterations 8 --alns-probability 0.35 \
  --capacity-scale 1.0 --repair-time-weight 0.05 \
  --output-dir outputs/pareto_wenchuan_baseline_20260809
```
